# libuipc-port → libuipc-origin Rebase（2026-04-22）

> 本次 rebase 的目的：让 `libuipc-port` 的 NVIDIA 路径与上游 `libuipc-origin/libuipc/`
> 字节等价，同时 corex 路径行为完全冻结。
>
> 关联文档：
> - [`porting-build-run-guide.md`](../../porting-build-run-guide.md)（§7.1 实测、§8 补丁清单 rebase 后状态）
> - [`corex-compat-policy.md`](corex-compat-policy.md)（baseline 升级说明）
> - [`corex-compat-audit-2026-04-17.md`](corex-compat-audit-2026-04-17.md)（旧 baseline 审计）

---

## 1. 背景

2026-04-20 在 RTX 5070 Ti 上跑完 5 个场景后发现：`libuipc-port` 的 NVIDIA 路径
（`-DUIPC_MUDA_USE_COREX=OFF`）在 wrecking_ball 场景上花了 **564.91s**，而同样的
upstream `libuipc-origin/libuipc` 只需 **46.58s**——12.13× 慢。其余 4 个场景虽然
绝对时间都 <40s，但仍然普遍比 origin 慢 1.1× ~ 14.7×（domino 33.40s vs 9.06s）。

诊断结论：`libuipc-port` 是一个**未 rebase 的旧 fork**，与 origin 之间存在数十处
非 corex-related 的算法/数据结构差异（PCG fix、对接配对策略、bvh 实现细节、
sanity checker 逻辑等），这些差异累积成了 wrecking_ball 上的灾难性减速。问题不
在 corex 隔离，而在 NVIDIA 路径自己被旧代码拖累。

---

## 2. 范围与原则

| 替换 | 保留 |
|---|---|
| `src/backends/cuda/`（除 `*_corex.*`） | 23 个 sidecar `*_corex.{cu,h,inl,cc.inc}` |
| `src/core/`（除 `*_corex.*`） | 22 个 switcher 的 `#if UIPC_COREX_CUDA10_COMPAT` 分支 |
| `src/geometry/`、`src/io/` 等其它 src/ 子目录 | `apps/examples/corex_demo/` |
| `include/`（公共头） | `docs/corex-compat-*`、`tools/audit/` |
|  | `external/muda/`（port 自带版本） |

**原则**：以 origin 的 cuda backend + core + 整个 src/ + include/ 为新的"NVIDIA
baseline"；NVIDIA 分支字节等价于 origin；corex 分支整体平移、原封不动。

## 3. 操作步骤（实际执行记录）

### Step 1 — 备份与基线快照

- 在 `libuipc-port/.rebase-snapshot/` 下保存：
  - `sidecars/`：23 个 `*_corex.*` + `details/corex_*` 文件（rebase 前快照）
  - `switcher-corex-branches/`：22 个 switcher 文件的 corex 分支抽取
  - `port-only-files/`：8 个 port-only 文件（joint external forces 等）
  - `full-pre-rebase/`：完整 `src/` + `include/`（1251 文件）应急回滚
  - `build_nvidia_meta/`：`CMakeCache.txt` + `corex_demo` 二进制
- 工具脚本：
  - `extract_corex_branch.py`：抽取 switcher 的 `#if UIPC_COREX_CUDA10_COMPAT` 分支
  - `wrap_switcher.py`、`rewrap_all.py`：按 origin body + corex 分支重新生成 switcher
- 物理备份原 `build_nvidia/`（用于事后回归对比）

### Step 2 — rsync origin → port（除 corex 文件）

```bash
rsync -av --delete \
    --exclude='*_corex.*' \
    libuipc-origin/libuipc/src/ \
    libuipc-port/src/

rsync -av --delete \
    libuipc-origin/libuipc/include/ \
    libuipc-port/include/
```

> rsync 范围比原计划广：起初只覆盖 `src/backends/cuda` + `src/core`，但
> `src/geometry/simplex_utils.cpp` 出现 `noexcept` mismatch 后扩展到整个
> `src/`，以保证所有源码与已更新的 `include/` 头文件一致。

### Step 3 — 重新打 22 个 switcher 包装

用 `.rebase-snapshot/rewrap_all.py` 把 origin 的实现重新包成
`#if UIPC_COREX_CUDA10_COMPAT … #else origin-body #endif`。两类处理：

- **20 个简单 switcher**：`#if` 分支只放一行 `#include "..._corex.<ext>"`
  （include 缩进 `#include` vs `#  include` 与 rebase 前快照保持一致）
- **2 个 inline switcher**：`type_define.h` / `contact_coeff.h` —— `#if` 分支放
  pre-rebase port 完整内容（含 muda triviality 特化等），`#else` 分支放 origin
  完整内容

§8 的 11 处补丁评估结果：A/D/E/F/H/I/J/K 已被 origin 上游覆盖，**只有 §B/§C
仍是 NVIDIA 分支特有的差异**（`abd_jacobi_matrix.{cu,h}`：corex 经
`abd_jacobi_matrix_corex.h` 仍 include `details/abd_jacobi_matrix.inl`，NVIDIA
分支需补 `<muda/atomic.h>`）。

### Step 4 — apps + cmake configure + ninja

- `src/backends/cuda/CMakeLists.txt`：在 `if(NOT UIPC_MUDA_USE_COREX)` 段加
  `list(FILTER SOURCES EXCLUDE REGEX ".*corex.*|.*details/corex_.*")`，否则
  GLOB_RECURSE 会把 sidecar 当独立 TU 编译，导致 NVIDIA 路径下编译失败。
- cmake configure 参数同 [`porting-build-run-guide.md`](../../porting-build-run-guide.md) §3.1。
- `ninja -j8` 一次成功。

### Step 5 — NVIDIA 路径 5 场景验证

| 场景 | 帧 | port pre-rebase | **port rebased** | origin | rebased vs origin |
|---|---|---|---|---|---|
| simple        | 200 |    1.20s |    **1.06s** |  1.07s | -0.6% |
| slope         | 200 |    2.45s |    **2.71s** |  2.71s | -0.1% |
| stack         | 200 |    3.77s |    **2.29s** |  2.28s | +0.4% |
| domino        | 300 |   33.40s |    **8.88s** |  9.06s | -2.0% |
| wrecking_ball | 400 | **564.91s** | **46.85s** | 46.58s | **+0.6%（12.06× 加速）** |

5 个场景全部 EXIT=0、0 sanity error、0 warning。

`tools/audit/verify_nvidia_branch_equiv.sh REF_DIR=libuipc-origin/libuipc/src`
报 **22/22 OK**，包括 §B/§C 在内（这两处的 NVIDIA 分支与 origin 字节等价，因为
origin 自身就是这种写法；港内的差异已经被 §B/§C 的 `#if/#else` 隔离到 corex
分支里）。

### Step 6 — corex 静态等价 + 远程实跑准备

本机静态校验（已通过）：

- `tools/audit/verify_corex_branch_equiv.sh`：22 个 switcher 的 corex 分支
  抽取 vs `.rebase-snapshot/switcher-corex-branches/` → **21 OK + 1 cosmetic**
  （`type_define.h` 仅末尾换行差异，对 C 预处理无影响）
- 23 个 sidecar 文件 vs `.rebase-snapshot/sidecars/` → **23/23 OK**

远程天数机器实跑（待执行）：

```bash
bash libuipc-port/tools/corex_remote_run.sh \
    --port-root  /path/to/libuipc-port \
    --vcpkg-root /root/vcpkg1          \
    --baseline   /path/to/nvidia-results    \
    --output     /path/to/corex-results-rebase \

```

脚本会输出 `diff_report.md`，列出每个场景末帧 OBJ vs baseline 的逐顶点 L2

- 所有 5 场景 EXIT=0、`Errors=0`

- mean L2 > 1e-2 m → 真回归；按"逐 switcher 回退" bisect 定位

## 4. 影响面与风险

### 4.1 NVIDIA 路径

- 字节等价于 origin（22/22 audit OK）。任何后续 origin upstream 升级，只需
  再次 `rsync --exclude='*_corex.*'` 然后跑 `rewrap_all.py` 即可。
- 性能与 origin 持平或略好（5 场景平均误差 ±2%），wrecking_ball 12.06× 加速。

### 4.2 Corex 路径

- 23 个 sidecar 文件 0 修改。22 个 switcher 的 corex 分支 0 语义修改
  （仅 `type_define.h` 末尾换行差异）。
- **风险点 1**：sidecar 引用的 origin 内部 helper 可能在升级中被改名/删除。
  本次 rebase 后未观察到（编译通过），但实际 corex 编译需要在天数机器上验证。
- **风险点 2**：origin 在某些场景的算法更激进，可能让 corex_demo 的 scene
  config 在 corex 上发散。本次承诺只 NVIDIA 路径对齐 + corex 路径行为不变；
  若发散，应在 sidecar 内部维持原 corex 行为，而非回退整个 rebase。

### 4.3 回滚

应急回滚（1 小时内）：

```bash
cd libuipc-port
rsync -av --delete .rebase-snapshot/full-pre-rebase/src/ src/
rsync -av --delete .rebase-snapshot/full-pre-rebase/include/ include/
cd build_nvidia && ninja -j8
```
