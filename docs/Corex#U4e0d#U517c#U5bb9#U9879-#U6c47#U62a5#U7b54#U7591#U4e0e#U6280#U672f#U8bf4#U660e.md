# Corex CUDA10.2 不兼容项 — 汇报答疑与技术说明

> 本文档配合《目前存在的问题.md》中的汇总表使用，用于下午汇报时**讲清每一项是什么、我们怎么处理的、对系统有什么影响**，以及**如何回应“这是不是 Corex 的问题”**这类追问。

---

## 1. 总体结论（建议开场先说清楚）

| 问题类型 | 说明 |
|---------|------|
| **CUDA 生态版本差异** | 多数条目对应的是 **CUDA Runtime / 数学库版本** 的能力差异（例如官方以 CUDA 11+ 为基准的新 API）。Corex 当前栈为 **CUDA 10.2 系**，与“较新教程/上游代码”假设的运行时不一致，**属于环境能力边界**，不是业务逻辑写错。 |
| **Corex 特有 vs 通用 10.2** | 一部分是 **任何 CUDA 10.2 环境都会遇到** 的（Graph 新 API、cuSolver 新 params API 等）；**另一部分**需要结合 Corex 实际提供的 **libcublas / libcusolver 动态库与符号** 是否完整，才能区分是“10.2 通用限制”还是“发行版裁剪/缺符号”。 |
| **我们的定位** | 适配层通过 **编译期分支、降级 API、可选能力** 让工程在 Corex 上**可编译、可加载、可运行**；**性能/功能上限**仍受运行时能力约束，若 Corex 提供更高版本或补齐符号，可逐步解除。 |

---

## 2. 逐项技术说明与“是否算 Corex 问题”的表述建议

### 2.1 CUDA Graph 新 API（`cudaGraphUpload` / `cudaGraphInstantiateWithFlags` / `cudaGraphAddMemcpyNode1D`）

**是什么：**  
CUDA Graph 在 **CUDA 11.x** 起对 API 做了扩展与增强（例如 upload、带 flags 的 instantiate、1D memcpy 节点等）。这些符号/语义在 **CUDA 10.2 的 cudart** 中不存在或不完整。

**我们怎么处理：**  
用 `CUDART_VERSION >= 11000` 分支：高版本走新 API；在 10.2 路径上 **退回旧 Graph API 或空实现**，保证编译通过。

**对系统的影响：**  
- 仍可编译、运行；  
- **缺少**新 Graph 路径上的部分优化（例如减少 launch 开销的 upload 流程），**偏性能/工程化**，不是“算错物理”。

**若被问“是不是 Corex 的 bug”：**  
更准确的表述是：**“上游代码按 CUDA 11+ 能力编写，而当前环境是 CUDA 10.2 runtime，属于版本能力差异；若 Corex 未来升级到与 CUDA 11+ 对齐的 cudart，可自然恢复新 API。”**

---

### 2.2 CUB ByKey Scan（`DeviceScan::Exclusive/Inclusive*ByKey`）

**是什么：**  
CUB 的 **按 key 分段** 的前缀和/扫描（segmented scan），依赖 CUB 版本与 Thrust/CUB 组合是否完整。在 **CUDA 10.2 + 配套 CUB** 上，部分 `*ByKey` 封装在实例化时容易失败或不可用。

**我们怎么处理：**  
在 `UIPC_COREX_CUDA10_COMPAT` 且低版本 runtime 下，**编译期不暴露** muda 里对 ByKey 的封装，避免整个工程被单一模板实例化拖死。

**对系统的影响：**  
- 全局 `ExclusiveSum/InclusiveSum` 仍可用；  
- **依赖“按 key 分段扫描”的算法**需要改写或关掉，功能面收缩。

**“是不是 Corex 问题”：**  
本质是 **10.2 时代 CUB 能力与上游封装假设不一致**。若 Corex 提供更新版 CUB 或文档说明支持的 CUB 版本，可再评估是否放开。

---

### 2.3 Thrust 执行策略（`thrust::cuda::par_nosync`）

**是什么：**  
`par_nosync` 是较新 Thrust 里的一种执行策略，**减少同步**、可能提高吞吐。旧版 Thrust 或定制发行版里**可能没有该符号**。

**我们怎么处理：**  
替换为 **`thrust::cuda::par.on(nullptr)`**，语义更保守、兼容性更好。

**对系统的影响：**  
- 正确性一般不受影响；  
- **可能略慢**（多同步），属于性能优化空间。

**“是不是 Corex 问题”：**  
属于 **Thrust 版本与上游代码假设不一致**。可问 Corex：**随附 Thrust 版本与 `par_nosync` 是否支持**；若未来对齐，可改回。

---

### 2.4 cuSolver Dense 新参数 API（`cusolverDnParams_t` + `cusolverDnXgetrf` / `cusolverDnXgetrs`）

**是什么：**  
cuSolver 在较新版本引入 **基于 `cusolverDnParams_t` 的 X 系列接口**（统一参数、更灵活的 dense 求解）。**CUDA 10.2 时代的 libcusolver 不包含这套完整能力**。

**我们怎么处理：**  
`#if CUDART_VERSION >= 11000` 才走新 API；否则 **编译期直接报错并返回**（或明确“该配置不支持”），避免链接到不存在的符号。

**对系统的影响：**  
- 依赖 **dense `gesv()` 等新 params 路径**的功能在 10.2 下**不可用**；  
- 其他仍可用旧 API 的求解路径不受影响（取决于 muda/libuipc 实际调用路径）。

**“是不是 Corex 问题”：**  
这是 **典型的 CUDA 主版本与 cuSolver 能力对齐问题**。若 Corex 长期固定 10.2，需接受该限制或提供等价 API；若升级 cuSolver/cudart，可再评估。

---

### 2.5 cuSolver Sparse 句柄（`cusolverSpCreate` 返回 `CUSOLVER_STATUS_NOT_SUPPORTED`）

**是什么：**  
`cusolverSp` 是 **稀疏** 线性代数相关句柄。部分发行版或裁剪版 **不提供 `cusolverSp`**，或 `cusolverSpCreate` 直接返回 `NOT_SUPPORTED`。

**我们怎么处理：**  
将 `cusolverSp` **视为可选**：创建失败则句柄置空，后续 `cusolverSpSetStream` 等调用加空指针保护，**不阻塞** `cusolverDn` 等 dense 路径初始化。

**对系统的影响：**  
- **强依赖 sparse cuSolver 的求解路径**无法工作；  
- 仅 dense 路径时，可能仍可用。

**“是不是 Corex 问题”：**  
这里**更贴近“Corex 发行包内容”**：若官方完整 libcusolver 应包含 Sp 且应成功创建，则值得向 Corex 确认 **是否裁剪、是否需额外包**；若文档明确不支持，则属**产品能力声明**问题。

---

### 2.6 cuBLAS 符号（`cublasNrm2Ex`）

**是什么：**  
`cublasNrm2Ex` 是 **通用数据类型** 的范数接口（支持多种 `cudaDataType`）。**部分 libcublas.so.10 构建**未导出该符号，会导致 `dlopen` 后 **undefined symbol**。

**我们怎么处理：**  
对 **`float` / `double`** 显式走 **`cublasSnrm2` / `cublasDnrm2`**；其余类型仍走 `Nrm2Ex`（若仍缺符号则仍可能失败）。

**对系统的影响：**  
- 常见双精度/单精度浮点路径可恢复；  
- **混合精度或非 float/double** 仍可能依赖 `Nrm2Ex`，存在风险。

**“是不是 Corex 问题”：**  
若 `nm -D libcublas.so.10` 确认 **无 `cublasNrm2Ex`**，则属于 **发行库与 NVIDIA 参考文档/符号集不一致** 或 **裁剪版**，应 **向 Corex 反馈补符号或提供兼容说明**。

---

### 2.7 RDC / Device Link（`-rdc=true`、`CUDA_SEPARABLE_COMPILATION`）

**是什么：**  
**Relocatable Device Code（RDC）** 允许跨多个 `.cu` 编译单元做 **device 符号链接**（类似主机侧多文件链接）。NVCC 默认用 `-rdc=true` + device link；**Clang 系 CUDA 前端（Corex）** 对 `-rdc`、设备链接参数与 CMake 集成**与 NVCC 不完全等价**。

**我们怎么处理：**  
在 Corex 模式下 **过滤 `-rdc=true`**，并关闭 `CUDA_SEPARABLE_COMPILATION` / `CUDA_RESOLVE_DEVICE_SYMBOLS`，先保证能完整编译。

**对系统的影响：**  
- 若项目**大量**依赖“跨 `.cu` 的 `__device__` 非 inline 函数互相调用”，可能需改结构；  
- 若主要依赖 **头文件内 inline/模板**（libuipc 多数如此），影响可有限。

**“是不是 Corex 问题”：**  
这是 **工具链差异（NVCC vs Clang-CUDA + Corex）+ CMake 集成** 的综合问题。可向 Corex 要：**官方推荐的 device link / RDC 用法与 CMake 示例**。

## 3. 可能被追问的简短回答模板

| 追问 | 建议回答 |
|------|----------|
| 这是不是你们代码写错了？ | 主要是 **运行时/SDK 版本与上游假设不一致**；我们已用分支与降级保证在 10.2 上可构建运行。 |
| 是不是只有 Corex 会这样？ | **任何 CUDA 10.2** 都会遇到 Graph 新 API、cuSolver params 等新接口问题；**缺符号/NOT_SUPPORTED** 要看具体发行包。 |
| 升级 CUDA 能解决吗？ | **多数条目会随 cudart/cuBLAS/cuSolver 升级缓解**；需 Corex 路线图与兼容性承诺。 |
| 你们最希望 Corex 提供什么？ | **明确的 cudart/cuBLAS/cuSolver 版本与符号表**；可选 **RDC/device link 官方文档**；长期 **对齐更高 CUDA 能力** 的路线图。 |
